# Event result capacity seam

The measurements and remaining-work tables below retain their dated source scope. By 17 October, subsequent shot analytics, scoring/point history, landing overlays/readers, mini-court history and optional activity storage had been repaired separately. Current evidence and limits are recorded in [the analytics capacity continuation](ANALYTICS_CAPACITY_SEAM_2026-10-16.md) and [point timeline note](POINT_ATTEMPT_TIMELINE_2026-10-16.md); none establishes actual full-match or live capacity.

The native YOLO26 pipeline already stores ball points and event features on disk. The next demonstrated growth was in event results: `_candidates_from_features()` converted the disk-selected features into a Python list; `_analyze()` additionally retained candidate, provisional, selected, event and trace lists. Phase 6 copied events with `sorted()` and `list()` and reconstructed complete dictionaries for three JSON arrays. This remains a capacity issue even while event authority is withheld: diagnostic candidates and traces are still produced.

The retained `artifacts/validation/yolo26_execution_2026-10-15/event_result_capacity_probe_v1` reproduction ran before this change. It extracted the actual existing SQLite feature store, selector, candidate factory and analysis control flow through the Python AST to avoid heavy imports. Synthetic scalar inputs retained 257, 1,025 and 4,097 live candidate objects; the 4,097-candidate case added 4,689,525 traced bytes. The actual analysis control flow with a synthetic verifier retained 1,025 candidates, events and traces as separate lists. The explicit bounded-object assertion failed as intended. Peak process RSS was 40,230,912 bytes, no heavy libraries or media were loaded, source hashes were unchanged and feature scratch was removed. This is evidence of result materialization, not measured match event frequency, vision accuracy or full-video capacity.

`src/utils/event_analysis_sequence.py` introduces a caller-owned `EventAnalysisSequence(directory)` context with three indexed snapshot sequences: `candidates`, `events` and `verification_traces`. It also owns the provisional ranking and accepted-event tables. Phase 6 enters the context through its existing `export_stack` and supplies `result_output` to `TennisEventDetector.analyze()` only for its native disk path. The feature store keeps its existing detector-local lifetime; the result store stays open through scoring, rendering and artifact export. `detector.last_analysis` references the same views and requires that owner context to remain open. The returned pipeline summary contains ordinary values, not live storage handles.

Omitting the new option preserves the list-based detector API, legacy candidate overrides and existing scratch-only behavior. Supplying a result output requires an open, empty store and explicit native feature scratch. Candidate selection writes one result at a time. Activity/provenance decisions and final temporal-suppression decisions explicitly write updated traces back to storage; mutating a decoded dictionary never changes a stored record implicitly.

The new store uses a 2 MiB SQLite cache, file-backed temporary sorting, disabled mmap and at most 256 writes per transaction. Typed candidate/event envelopes reuse the existing safe private container codec. Tuples, lists, nested dictionaries, NumPy numeric payloads and IEEE float bits remain snapshots rather than pickle objects. Unranked evidence can retain signed zero and nonfinite IEEE payloads. Active sorting and suppression keys must be finite, exactly representable binary64 numbers; values are not silently normalized into SQLite NULL or coerced from arbitrary text.

Final selection preserves the existing key order: descending confidence, timestamp, then candidate ID. Accepted events are emitted by timestamp with stable rank order, after which sequential event IDs and final trace fields are persisted. Suppression first queries outward-rounded indexed time bounds, then applies the original inclusive `abs(timestamp - kept_timestamp) <= interval` predicate. The existing optional spatial branch also suppresses all events inside the final time interval; this change preserves that behavior and does not redefine its semantics.

The result owner removes only its exclusively created database and exact SQLite sidecars on successful, failed and cancelled exits, including when a frame-query producer is suspended. It does not delete the caller directory or unrelated files. Stored results are temporary offline analysis artifacts, not a temporal-filter checkpoint or supported crash-resume state. Completed JSON destinations retain the existing atomic per-file publication behavior.

Phase 6 uses indexed frame ordering for its scoring pass, retains a sequence alias for authoritative native events, queries a small frame interval for event badges and streams historical bounce snapshots for the mini-court. Landing-zone enrichment explicitly writes event evidence back so its JSON export sees the same changes. `match_events.json`, `event_candidates.json` and `event_verification_trace.json` are serialized one record at a time using the existing `JsonArrayArtifact` writer. Loaded JSON keys, values, rounding and authority separation remain unchanged; whitespace is not a byte-level compatibility promise.

Current production configuration has `authoritative_enabled: false`, so downstream authoritative event collections are empty. That preserves the qualification gate and does not qualify events merely because their storage became bounded. The full 10-minute/30-minute/2–3-hour resource runs, durable inference recovery, qualified events and real live operation remain unproven. This change closes one demonstrated result-storage seam; it cannot justify a claim that complete match analysis is now bounded.

Focused verification is in `tests/test_event_analysis_sequence.py`: actual detector legacy/disk equality, typed payload snapshots, exact ranking endpoints and ties, persistent trace decisions, constant live candidate objects across commit boundaries, indexed frame queries, owner lifetime, cancellation cleanup and loaded JSON wire values. Phase 6 export helpers can be checked without importing its model runtime by extracting those exact functions; that limited check is distinct from an end-to-end pipeline run.

`ShotEvidenceSequence` now owns typed shot snapshots, a 2 MiB SQLite cache, disabled mmap, file-backed temporary ordering and at most 256 writes per transaction. Phase 6 enters that owner through its existing export stack. The linker's opt-in path requires the exact authoritative event sequence alias and uses two indexed event reads with one-hit lookahead, retaining only current/following hit and current bounce evidence. It preserves the existing strict `hit_frame < bounce_frame <= next_hit_frame + 5` rule, stable equal-frame ordering and reuse of one bounce for multiple nearby hits. It does not infer event authority. The default API still returns a list, and an empty withheld-authority input remains empty without reading diagnostic events. Snapshots require explicit indexed writeback; existing downstream consumers do not mutate shot objects.

Native shot badges query only the inclusive preceding twenty-frame window. The query retains the previous dictionary's last record per frame and first-insertion order, including duplicate hit frames. `shot_events.json` streams one sanitized record at a time, preserving loaded JSON values and existing enum semantics. Storage and active readers close on success, exceptions and cancellation, removing only owned databases and exact sidecars. This remains temporary offline storage; no checkpoint or crash-resume claim is added.
