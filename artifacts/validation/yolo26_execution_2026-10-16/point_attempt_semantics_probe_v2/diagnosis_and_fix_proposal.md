# Point, attempt and service-context correctness seam — read-only proposal

The current native pipeline loses explicit rule boundaries between scoring and analytics. It cannot report correct point/rally membership or serve-attempt statistics by passing the final match state to one whole-file group. This proposal is a coherent replacement of that semantic handoff; changing only the rally counter, a serve percentage or the FPS calculation would leave the same wrong memberships authoritative.

No production source was edited. The actual real `TennisScoringEngine` and `PointOutcomeResolver`, actual shot linker/classifier/direction/zone class AST and exact Phase6 step-7/step-10/export statements were executed. The inputs are small, explicit synthetic contacts, line-call decisions, identity/end confirmations and PTS fixtures. They establish software behavior only. The geometry engine was replaced by supplied typed `LineCallEvidence` in the main probe, and every requested context/target was recorded; no line-call or event accuracy is established.

## Proposed smallest coherent native interface

Create a model-free point/attempt timeline reducer plus a caller-owned indexed ledger. The reducer owns one active point, one active serve execution and one provisional/legal rally at a time. The ledger stores completed and partial records and membership; no list of all points, attempts, events, shot IDs or timing samples is introduced.

1. Add `src/scoring/point_timeline.py` for typed transition/context records and the pure reducer. Its input is an immutable **pre-event** scoring snapshot, the source event key, verified rule signal/line-call reference, source-clock/camera/identity eligibility and the returned outcome plus post-event state. Its output is point/attempt/rally state changes with explicit statuses and reason codes. It must not infer a point boundary from a time gap, a new serve contact alone or the final match state.
2. Add `src/utils/point_analysis_sequence.py` as the native caller-owned SQLite ledger, or equivalently add the same typed tables behind the current event owner. Prefer a separate small deep module to avoid widening the physical event codec. It has the existing storage policies: cache at most 2 MiB, mmap disabled, file-backed temporary work, commits of at most 256 writes, registered reader cleanup and exact owned-file cleanup. Tables index transitions by source event key/revision, points by anchor/status, serve executions by point/official slot/replay index, rallies by point, and shot memberships by source event key/shot position. A sealed view supplies ordered point/attempt/rally/ID selections to analytics/export.
3. Add an explicit native `timeline_output`/`event_context` option at the scoring handoff. Capture `state.to_dict()` and resolver phase **before** calling the real resolver, then persist the returned explicit `PointOutcome` including `is_point_ending` and winner. Preserve existing legacy return tuples and list APIs by default. The public scoring phase must stay consistent with the resolver: serve contact means `SERVE_STARTED` and first/second serve in progress; legal service bounce means `LIVE`. This can be a distinct `SERVE_ATTEMPT_STARTED` outcome or an explicit typed phase on the outcome. Do not distinguish them by parsing `reason` strings.
4. Phase6 step 7 obtains context from the exact current `candidate_frames[frame]` source/camera/identity owner and the current eligible registration. It creates the ledger in `export_stack`, records the pre-event context, processes the event, records the outcome and updates the timeline. Remove service-end guessing. A verified service context with unknown target must produce an unavailable/review result **before** geometric evaluation; the line-call method must independently abstain on a missing native service target as well, rather than retain its default. The target must bind eligible match identity, current court-end evidence, camera segment, calibration/identity revisions and the **pre-event** service side. Missing, stale or conflicting context withholds the call; near/far role IDs, configured participant numbers and bounding-box ground proxies do not establish that evidence.
5. Step 9 joins contacts and bounce links to this ledger by source event key. It preserves all physical shot observations but attaches explicit `point_uid`, `attempt_uid`, `rally_uid`, attempt result, play scope and eligibility/reason. A first-fault contact receives an explicit fault attempt result; a let remains a replayed execution; neither enters legal rally counts. The original `is_dead_ball` field continues to describe contacts observed after play was already dead. Restrict eligible contact/bounce associations to the same point/attempt scope and valid interval; the current `next hit + 5 frames` heuristic must not cross a fault, let, point conclusion, consequential gap or unresolved boundary. Ambiguous links remain unknown.
6. Step 10 consumes sealed ledger selections, rather than asking the old one-group APIs to discover boundaries. It exports one record per anchored completed/partial point and per legal/provisional rally, plus serve-execution records. Membership arrays and match heatmaps use the current incremental atomic writers. Native return values contain artifact references/counts; no closed owner escapes. Use a versioned native analytics schema for the added semantic fields/statuses, retain useful existing array names, and preserve explicit legacy APIs for old callers. No current frontend/API source directly consumes `serve_analytics` or the point/rally files in the searched paths; still verify adapters/contracts when wiring the native v2 artifacts.

### Point and attempt rules

An anchored point begins with a serve whose pre-event rule state, server and source context are known. `FIRST_SERVE_FAULT` closes the first execution, opens the same point's second slot and does not create a completed point or live rally. `SERVICE_LET` closes an execution with replay status; the next serve uses the same official slot and a new replay index. `DOUBLE_FAULT` closes that point with the explicit receiver winner and no legal live rally. A terminal legal-rally outcome closes its own point with that outcome's winner/reason and pre-point score context. The next-point reset and next game's server/side must never relabel the completed point.

Unknown initial score/server, mid-clip contacts, unresolved service legality or a consequential gap produce explicit partial/provisional/review records. Retain the observations and their reason; do not assign a winner, official attempt or match game number that has no confirmed anchor. A review-required outcome freezes authoritative score progression and cannot start new authoritative points from subsequent contacts until an explicit correction/re-anchoring revision resolves the gap. An unsupported let detector must not be fabricated: a rule signal must reference an authorized reviewed source or independently verified evidence. Camera/source ineligibility can create a review/gap signal bound to the actual interval audit, not a fabricated physical event.

### Stable identity, revision and timing

Use string UIDs bound to `analysis_id`, source-video/event-artifact fingerprint, analysis/rule revision and the relevant source event anchor. Preserve numeric display indices separately. A point UID uses its opening confirmed serve or explicit partial anchor; an attempt UID adds official slot, replay index and contact event key; a rally UID adds the legal-play anchor. Source event keys retain source frame/PTS/time base and event identity within its frozen artifact. Idempotency is enforced by unique ledger keys, not an in-memory set of all event IDs. Corrections create a new revision and retain explicit supersession/audit links; they cannot silently change views from a sealed revision.

For duration, resolve start and actual terminal **event** source references from `candidate_frames` before converting to float. Use exact rational PTS/time-base arithmetic, including time-base changes and large offsets. A complete eligible rally with verified normal-speed continuity can report terminal-source-time minus legal-start-source-time. A missing/reversed clock, replay, cut, unsupported speed change or consequential gap makes full rally duration unavailable. Separately labeled observed eligible-time coverage may be accumulated from known consecutive intervals; it must not masquerade as full physical rally duration. A source-playback elapsed time without normal-speed qualification is metadata, not verified real-play elapsed time. No FPS fallback or last-hit-only timestamp fallback is permitted for a native qualified duration.

Service context also requires a current eligible identity-to-court-end mapping, not just stable A/B identity and not just a rules-predicted end. End changes invalidate/advance that context; cuts, camera flips, zoom/recalibration revisions and stale identity require current revalidation. The current production candidate path has no qualified such mapping, so it must continue withholding these measurements.

### Serve denominators and bounded ownership

Compute per-player statistics from attempt results, not from a list of all `ShotType.SERVE` contacts selected using the final server. Keep first/second official slots, contact execution counts and lets distinct. A let/replay does not create a second official first-attempt slot. First/second successes and faults require explicit resolved outcomes; double faults require the explicit terminal outcome. Report unresolved attempts and known-outcome coverage. Define the percentage denominator in the schema, e.g. resolved first slots `first_in + first_fault`, and return unavailable when that denominator is absent. Do not silently count unresolved/mid-clip contacts as first faults, first serves in, or zero errors. Placement needs qualified landing/court/identity context and otherwise stays unknown.

The current scoring engine itself retains `_inputs`, history entries, processed-ID sets and correction histories. Adding an indexed timeline while duplicating every transition into more Python lists is insufficient. The native ledger backend should also provide the history/idempotency/input views used by scoring, while legacy default `ScoreEventHistory` remains unchanged. Native correction must stream the old revision's inputs into a fresh owned revision, applying the reviewed replacement, and publish/swap only after a successful complete replay. It must not call the existing whole-list `deepcopy` path on a live ledger. If history migration is deferred, it remains an explicit blocker to a full-match bounded-memory claim; the new seam may not introduce additional growth or claim that the old history growth is solved.
